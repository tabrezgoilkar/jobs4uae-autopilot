# Phases 5–7 — Batch Plan (PDF Export · Tracker · GCC Scanning)

> Built in **parallel** by three agents (isolated worktrees), each producing only its own new files. The lead (controller) owns the shared wiring + Playwright browser download + integration + final review. Shared deps already added: `playwright`, `cheerio`, `marked`. Shared helper already added: `server/lib/browser.js` (`renderPdfFromHtml`, `fetchHtml`) — agents import it and **mock it** in tests.

## Cross-cutting rules (all three agents)

- **Do NOT edit** these shared files (the lead wires them at integration): `server/app.js`, `web/src/App.tsx`, `web/src/components/Layout.tsx`, `web/src/api.ts`. Instead, report the exact wiring needed.
- Each phase gets **its own web API-client file** under `web/src/features/<phase>/` and **its own page component**, so there are no shared-frontend collisions.
- **Route tests** mount the router on a **local express app** in the test (`const app = express(); app.use('/api', xRouter());`) — not the global `createApp()` — so they pass without touching `app.js`.
- Follow existing patterns: JSON-file stores like `server/evaluate/store.js`; routes return `{ error }` with 400/404/409/500; engines normalize AI JSON; reuse `server/lib/json.js` `extractJson` and `server/lib/grades.js`.
- TDD throughout. Commit on the agent's own branch. Frontend verified by `npm --prefix web run build` (zero TS errors).

## Phase 5 — PDF Export (agent A)

**Goal:** Download a generated resume + cover letter as a polished **PDF**, defaulting to a **UAE/GCC-style resume template**.

**Files (new only):**
- `server/documents/pdf/template.js` — `resumeHtml(profile, resumeMarkdown, opts)` and `coverLetterHtml(profile, coverLetterMarkdown, opts)` → full HTML strings. Resume uses a **UAE template**: header (name + contact), a **Personal Details** block (nationality, visa status, notice period, languages, driving licence — pulled from profile if present, blank otherwise), then the Markdown body rendered via `marked`. Clean print CSS inline.
- `server/documents/pdf/render.js` — `renderResumePdf(...)`, `renderCoverLetterPdf(...)` → call `renderPdfFromHtml` (from `server/lib/browser.js`) on the template HTML; return a Buffer.
- `server/routes/pdf.routes.js` — `pdfRouter()`: `POST /documents/:id/pdf?kind=resume|cover` → load the saved document + profile, render, respond with `application/pdf` (Content-Disposition attachment). 404 if doc missing; 400 if kind invalid.
- Tests: `server/__tests__/pdf-template.test.js` (HTML contains the name + a Personal Details heading + rendered markdown), `server/__tests__/pdf-render.test.js` (mock `../lib/browser.js` `renderPdfFromHtml` → returns a fake Buffer; assert called with HTML containing the name), `server/__tests__/api-pdf.test.js` (local-express; mock render; assert 200 + `content-type: application/pdf`, 404 for missing doc).
- Frontend: `web/src/features/pdf/pdfApi.ts` (`downloadPdf(docId, kind)` → fetch the PDF blob, trigger browser download) and a **Download buttons** addition delivered as a small component `web/src/features/pdf/DownloadButtons.tsx` (Resume PDF / Cover Letter PDF). *Do not edit DocumentsPage* — the lead will drop `<DownloadButtons docId=… />` into it.

**Wiring to report:** mount `pdfRouter()` in app.js; place `<DownloadButtons>` in DocumentsPage near the Save button.

**Acceptance (lead runs):** generate docs → click Resume PDF → a valid PDF downloads in the UAE template.

## Phase 6 — Application Tracker (agent B)

**Goal:** Track applications with statuses; persists across restart.

**Files (new only):**
- `server/tracker/store.js` — JSON-file store `data/applications.json`: `listApplications()`, `addApplication(app)` (id + createdAt + updatedAt, newest first; strips client id/timestamps), `getApplication(id)`, `updateApplication(id, patch)` (e.g. status/notes; strips id/createdAt), `deleteApplication(id)`. Status enum: `saved` → `applied` → `interview` → `offer` → `rejected` (validate; default `saved`).
- `server/routes/tracker.routes.js` — `trackerRouter()`: `GET /applications`, `POST /applications` (create: jobTitle, company, location, status, notes, evaluationId?, documentId?), `GET /applications/:id`, `POST /applications/:id` (update status/notes), `POST /applications/:id/delete` (or `DELETE`). `{error}` shapes + 404.
- Tests: `server/__tests__/tracker-store.test.js` (add/list/get/update status/delete, persistence via temp dir + `vi.resetModules()`), `server/__tests__/api-tracker.test.js` (local-express; full CRUD + invalid status rejected 400).
- Frontend: `web/src/features/tracker/trackerApi.ts` (list/create/update/delete) and `web/src/pages/TrackerPage.tsx` — a board/list grouped by status with the 5 columns/sections, add-application form, status change (dropdown or move buttons), notes, delete. Friendly, hardened (try/catch/finally, disabled states, a11y labels) like ProfilePage/DocumentsPage.

**Wiring to report:** mount `trackerRouter()`; add `/tracker` route + "Tracker" nav link; (optional) a Dashboard CTA.

**Acceptance (lead runs):** add applications, change statuses, delete → all persist across restart.

## Phase 7 — GCC Scanning Tier 1: Bayt + Naukrigulf (agent C)

**Goal:** Search Bayt + Naukrigulf by keyword/country/city → normalized listings the user can one-click evaluate.

**Files (new only):**
- `server/scanner/boards/bayt.js`, `server/scanner/boards/naukrigulf.js` — each exports `{ id, name, buildSearchUrl({keyword,country,city}), parseListings(html) -> [{title, company, location, url, source}] }`. Parsing uses `cheerio`. Selectors are best-effort + defensive (skip malformed nodes).
- `server/scanner/engine.js` — `scan({board, keyword, country, city})`: resolve board config, `fetchHtml(buildSearchUrl(...))` (from `server/lib/browser.js`), `parseListings`, return normalized listings. Graceful: a board/parse failure returns `{ listings: [], error }` not a throw.
- `server/scanner/store.js` — optional cache `data/scanned-jobs.json` (list/add). Keep minimal.
- `server/routes/scanner.routes.js` — `scannerRouter()`: `GET /scanner/boards` (list supported boards), `POST /scanner/scan` ({board, keyword, country, city}) → `{ listings, error? }`. Validate board; 400 on missing keyword.
- Tests: `server/__tests__/scanner-bayt.test.js` + `scanner-naukrigulf.test.js` (`buildSearchUrl` shape; `parseListings(fixtureHtml)` → expected listings from a small inline fixture string), `server/__tests__/api-scanner.test.js` (local-express; mock `../lib/browser.js` `fetchHtml` → fixture HTML; assert listings; board failure → graceful `{listings:[], error}`; 400 missing keyword).
- Frontend: `web/src/features/scanner/scannerApi.ts` (boards + scan) and `web/src/pages/ScanPage.tsx` — pick board + keyword + GCC country/city → Scan → results list, each with an **"Evaluate"** action that POSTs the listing's text to the existing `/api/evaluate` (reuse the existing evaluate client by calling `fetch('/api/evaluate', …)` directly inside scannerApi to avoid editing shared api.ts). Hardened UX; clear "couldn't read this board right now" message on `error`.

**Honesty:** parsing is selector-dependent and may need live tuning; tests use fixtures. Mark live scraping as needing real-world verification.

**Wiring to report:** mount `scannerRouter()`; add `/scan` route + "Find Jobs" nav link.
